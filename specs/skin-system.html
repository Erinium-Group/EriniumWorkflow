Systeme de Skin Custom

Permettre a chaque joueur de telecharger un skin personnalise depuis le site web et de le voir applique en jeu pour tous les autres joueurs sur le serveur.

Site web + Mod Auth Bearer JWT Termine

Contexte

Le serveur EriniumFaction tourne en client moddé et le launcher gere l'authentification. Mojang n'expose pas de skins pour les comptes non premium (ou les comptes premium ont leur skin Mojang affichee, ce qu'on veut ecraser). On prend la main sur le rendu du skin pour offrir un systeme propre a la communaute : le joueur uploade son skin sur le site, et tous les clients connectes voient ce skin sur son personnage.

Cible : 500-1000 joueurs concurrents. Le systeme doit etre asynchrone (telechargement HTTP hors du tick), mis en cache cote client, et resistant aux erreurs reseau (fallback Steve).

Objectifs

  • Page profil sur le site avec viewer 3D du skin courant et bouton d'upload (drag & drop + clic).
  • Validation stricte cote serveur : PNG 64x64 (vrais bytes IHDR, pas seulement le nom de fichier ou content-type), 100 KB max.
  • Stockage : un fichier par UUID Minecraft ({uuid}.png), ecriture atomique.
  • Endpoint public servant le skin avec fallback Steve (404 -> steve.png).
  • Cote mod : a la connexion, le serveur diffuse l'URL du skin de chaque joueur. Le client telecharge en async et substitue la texture par defaut.
  • Aucun impact sur le tick : I/O HTTP en thread separe, cache RAM cote client.

Architecture

   |  upload PNG
   v
[Site Next.js]  ---POST /api/profile/skin---> valide PNG 64x64 + IHDR
   |
   |  fs.rename atomique  -> public/skins/{uuid}.png
   v
[Filesystem]                      <--- GET /api/skin/{uuid}.png  (public)
                                                   |
                                                   |
[Serveur Minecraft] ---broadcast SyncSkinPacket(uuid, url)---> [Clients]
   PlayerLoggedInEvent                                             |
                                                                    |  fetch async (HttpURLConnection en thread)
                                                                    v
                                                            [DynamicTexture cache UUID -> ResourceLocation]
                                                                    |
                                                                    v
                                                            Mixin AbstractClientPlayer.getLocationSkin
                                                                    -> retourne la texture custom ou null (fallback vanilla)

Stockage

Filesystem

Les skins sont stockes a plat dans EriniumFactionWeb/public/skins/{uuid}.png. L'UUID est la valeur users.mc_uuid de la base, normalisee (lowercase, avec ou sans tirets — choix : avec tirets pour matcher le format Minecraft canonique).

Ecriture atomique

L'upload ecrit d'abord dans public/skins/{uuid}.png.tmp puis renomme via fs.rename (atomique sur le meme volume). Un GET concurrent ne verra jamais un fichier partiel.

API Web

POST /api/profile/skin

Auth requise. Multipart form-data, champ file. Reponse 200 :

{ "url": "/api/skin/<uuid>.png" }

Codes d'erreur :

  • 401 - non authentifie
  • 400 - aucun fichier, fichier trop gros, dimensions != 64x64, signature PNG invalide
  • 409 - utilisateur n'a pas lie son compte Minecraft (mc_uuid null)
  • 500 - erreur d'ecriture

GET /api/skin/<uuid>.png

Public, sans auth. Sert le PNG du joueur ou public/steve.png en fallback. Cache HTTP : Cache-Control: public, max-age=60.

Note : on garde un cache court (60s) parce que le skin peut etre change. Le mod ajoute un parametre ?v=<timestamp> pour forcer le refetch a la connexion.

Cote Mod

Packet SyncSkinPacket

Channel eriniumfaction_skin, message ID 0, sens SERVER -> CLIENT.

class PacketSkinSync {
    UUID playerUuid;   // 16 bytes
    String skinUrl;    // varchar UTF-8
}

Cote serveur

  • A PlayerLoggedInEvent, le serveur calcule l'URL {siteUrl}/api/skin/{uuid}.png?v={now} pour le joueur qui rejoint.
  • Il broadcast un packet a tous les joueurs contenant l'UUID et l'URL du nouveau venu.
  • Il envoie aussi au nouveau venu les URL des joueurs deja connectes.

Cote client

  • SkinCache : Map UUID -> ResourceLocation, ConcurrentHashMap.
  • A reception du packet, lance un thread dedie qui fait HttpURLConnection.getInputStream, charge un BufferedImage, le stocke dans une DynamicTexture, l'enregistre dans le TextureManager sur le main thread (via Minecraft.addScheduledTask), puis cache la ResourceLocation.
  • MixinAbstractClientPlayer sur getLocationSkin() : delegue a SkinHook.getSkin(uuid). Si non null, le retourne ; sinon laisse le rendu vanilla (qui sera Steve par defaut).
  • Hook setup dans ClientProxy.init() (pattern Banner identique : SkinHook.getSkinForUuid = SkinCache::get).
  • Sur ClientDisconnectionFromServerEvent : vide le cache (libere la GPU).

Fallback Steve

assets/eriniumfaction/textures/entity/steve.png est embarque dans le mod. Si le fetch HTTP echoue ou retourne un PNG invalide, le client tombe automatiquement sur la skin vanilla (qu'on n'ecrase pas). Le serveur web fait pareil de son cote (404 -> public/steve.png).

Cas limites

  • Joueur sans mc_uuid : impossible d'uploader (409). Le mod renvoie alors steve.png par defaut.
  • PNG malformme : signature checkee (8 bytes magic + chunk IHDR a l'offset 8), dimensions lues depuis IHDR. Refus 400 si != 64x64.
  • Fetch HTTP timeout cote client : 5s connect / 10s read. En echec : pas de retry, le joueur reste sur Steve. Re-tentative au prochain login.
  • Joueur change de skin en jeu : a chaque upload, le serveur web peut notifier le serveur Minecraft via une route admin (future feature). En v1 : refresh au prochain login uniquement.
  • 500 joueurs simultanes : le broadcast de SyncSkinPacket au login d'un joueur envoie 500 packets de ~80 bytes -> ~40 KB, negligeable. Le receiver-side fetch est etale dans le temps (pas tous au meme instant).

Plan de tests

  1. Upload d'un PNG 64x64 valide -> 200, fichier present, viewer 3D refresh.
  2. Upload d'un JPG -> 400 (signature PNG manquante).
  3. Upload d'un PNG 32x32 -> 400 (dimensions IHDR != 64x64).
  4. Upload d'un PNG > 100 KB -> 400.
  5. Upload sans auth -> 401.
  6. Upload sans mc_uuid lie -> 409.
  7. GET d'un UUID inconnu -> sert steve.png avec 200.
  8. En jeu : 2 joueurs avec skin uploade -> chacun voit le skin de l'autre dans les 2 secondes apres login.
  9. En jeu : un joueur sans skin uploade -> rendu Steve.
  10. Profiling TPS : aucune regression mesurable a 500 joueurs.
