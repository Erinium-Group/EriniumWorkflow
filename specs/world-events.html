Evenements Mondiaux

Systeme global d'evenements declenches automatiquement par un scheduler central — meteor shower, rifts dimensionnels, marchand noir ambulant, boss mondial — concu pour animer un serveur de 500 a 1000 joueurs sans intervention staff.

Planifie Scheduler global PvX emergent Butin progressif Anti-camp Persistant Boss Mondial

01 Contexte & Objectifs

Vision du systeme

Les Evenements Mondiaux sont des animations recurrentes du serveur : un meteor shower nocturne, un rift dimensionnel qui s'ouvre quelque part dans le monde, un marchand noir qui apparait sans prevenir, un boss mondial qui ravage le centre de la carte. Ces evenements creent du contenu emergent : la course au butin, la confrontation entre factions, le rush coordonne.

Sur un serveur de 500 a 1000 joueurs simultanes, ces evenements remplacent les events organises manuellement par le staff. Le scheduler tourne en continu, choisit les events selon une rotation ponderee, les annonce, les execute, et nettoie derriere lui. Aucune intervention humaine n'est requise.

Objectifs de design

  • Rythme constant : au moins un evenement actif par tranche de 2 a 4 heures. Le joueur qui se connecte sait qu'il aura "toujours quelque chose a faire".
  • Equite d'acces : les evenements sont publics, multi-factions. Pas de favoritisme. Le butin est distribue selon la contribution reelle (degats, kills, recolte).
  • Anti-camp : les coordonnees exactes ne sont jamais dans l'annonce. Le joueur doit chercher (zone approximative, indices, particules visibles a distance).
  • Pas de staff requis : tout est automatique. Le staff peut juste cancel, start, schedule via commandes admin pour les cas particuliers (event communautaire, evenement special).
  • Performance : sur 500-1000 joueurs, chaque event doit etre dimensionne (entites cap, AI ticking optimise, packets batch). Aucun event ne doit faire chuter le TPS sous 18.
  • Equilibre du butin : les recompenses sont progressives. Meteor Shower = ressources moyennes courantes. Rift = items rares. Marchand Noir = items premium achetables. Boss Mondial = legendaires + Eris.

Ce que le systeme ne fait pas

  • Pas d'event en boucle infinie : chaque event a une duree fixe et une fin propre. Pas d'event "permanent".
  • Pas de matchmaking : pas d'inscription, pas de file d'attente. L'event est ouvert a tous, dans le monde, en meme temps.
  • Pas de zones safe pendant l'event : les claims faction protegent toujours. Les events ne forcent pas le PvP sur les zones de spawn.
  • Pas d'event hors monde principal : tous les events se deroulent dans la dimension overworld custom Erinium (sauf Rift qui cree une instance dimension dediee).
ⓘ
Charge cible : 500 a 1000 joueurs simultanes. Le systeme doit fonctionner avec 1 a 50 joueurs reellement presents sur l'evenement (les autres etant occupes ailleurs). Aucun evenement ne suppose une participation minimale au-dela d'un minPlayersOnline global.

Distribution du butin (boss mondial)

La Map<UUID, Long> damageDealt est utilisee pour distribuer le butin de fin. Apres tri par valeur decroissante :

  • Top 1 (killer) : 25 % du loot pool + bonus "first blood".
  • Top 2-10 : repartition ponderee selon le pourcentage de degats du total.
  • Tous les autres (damage > 1% du total) : butin de consolation (1 lootbox basique + 100 Eris).
  • Damage < 1% : rien (anti-leech).

04 EventManager & Scheduler

Cycle de vie complet

[Server boot] | v EventManager.init() - Charge events.cfg + JSON par event - Charge EventSavedData (WorldSavedData) - Reprend les events actifs (state = ACTIVE) si reboot pendant un event - Calcule le prochain declenchement (random ponderee) | v EriEvents.on(ServerTickEvent).phase(END) | v [Toutes les 20 ticks (1 sec)] - evaluate scheduled queue : si head.scheduledTick <= now -> ANNOUNCING - tick chaque EventInstance ACTIVE -> event.onTick(inst) - check end : si now >= inst.endTick -> ENDING -> onEnd - check cleanup : si state == COMPLETED depuis 5 min -> supprime - save markDirty() WorldSavedData toutes les minutes | v [Selection du prochain event] - Filtre les events disponibles (cooldown OK, nuit/jour, players OK) - Tirage aleatoire pondere par event.getWeight() - nextScheduledTick = now + random(minInterval, maxInterval) - ajoute a la PriorityQueue scheduled

Integration EriScheduler

Le tick principal utilise EriEvents.on(TickEvent.ServerTickEvent.class).phase(Phase.END).handle(...). Une optimisation : ne pas evaluer chaque tick mais toutes les 20 ticks (1 sec). Compteur tickCounter % 20 == 0.

Pour les actions a effectuer plus tard (annonces T-10min, T-1min) : EriScheduler.delay(ticks, () -> ...). Le scheduler EriAPI gere la dispatch sur le thread serveur.

Calendrier des evenements

  • Rotation aleatoire ponderee : chaque event a un weight (1-100). Plus le poids est eleve, plus l'event est probable.
  • Cooldown anti-repetition : chaque event a son propre cooldownTicks. Apres execution, il est marque indisponible pendant ce cooldown.
  • Global cooldown : entre la fin d'un event et le debut du suivant : 30-60 min (configurable).
  • Anti-collision : max 2 events simultanes par defaut. canRunConcurrently() permet a un event de refuser de tourner avec un autre (ex : Boss Mondial bloque Meteor Shower).

Cycle jour / nuit

Le serveur tourne sur le monde Erinium custom (overworld remplacant). La nuit est definie par world.getWorldTime() % 24000 dans l'intervalle [13000, 23000].

  • Events nuit-only : Meteor Shower. Si la fenetre nuit se ferme avant la fin de l'event, l'event continue mais aucun nouveau meteor n'est spawne (decroissance naturelle).
  • Spawn time-shift : si un event nuit-only est tire mais qu'on est en plein jour, son scheduledTick est repousse au prochain debut de nuit + petit delay aleatoire (anti-predictibilite).

Persistance WorldSavedData

EventSavedData etend WorldSavedData. Stocke :

public class EventSavedData extends WorldSavedData { private static final String DATA_NAME = "eriniumfaction_events"; List<EventInstance> activeEvents; // Events en cours Map<String, Long> eventCooldowns; // eventId -> tick de fin de cooldown long lastEventStart; // Global cooldown long nextScheduled; // Prochain event prevu String nextEventId; Map<UUID, Integer> playerStats; // "events participated" totaux }
⚠
Reprise apres restart : Si le serveur crash pendant un event ACTIVE, le EventSavedData est rechargee au boot. Les events sont re-instancies, leurs entites re-localisees par UUID, et le tick courant ajuste pour que endTick soit relatif au moment du crash + temps restant. Si une entite essentielle a disparu (boss, marchand), l'event est annule proprement avec compensation aux contributeurs.

Configuration JSON par event

Chaque event a son fichier dans config/eriniumfaction/events/<event_id>.json. Charge par EventConfig.loadEventConfig(eventId) au boot. Si le fichier n'existe pas, valeurs defaut + fichier ecrit.

// config/eriniumfaction/events/meteor_shower.json { "enabled": true, "weight": 40, "durationMinutes": 20, "cooldownHours": 4, "meteorCount": { "min": 100, "max": 300 }, "spawnRadius": 500, "spawnHeight": 200, "impactExplosionLevel": 1, "loot": "eriniumfaction:events/meteor_shower", "announce": [600, 60, 0] }

  • Recoit un packet S2C_EventToast contenant : String eventId, String titleKey, String subtitleKey, int color, int durationTicks.
  • Animation : slide-in depuis le haut (300ms, easing EASE_OUT_CUBIC), pulse couleur, slide-out (300ms, EASE_IN_CUBIC).

ⓘ
Anti-camp : Les annonces donnent une zone approximative (ex : "secteur nord-est" ou "rayon de 500 blocs autour de [x ~1000, z ~-500]") mais JAMAIS les coordonnees exactes. Le joueur doit chercher visuellement (particules de portail, lueur du boss visible a 200 blocs, traces de meteores).

06 Meteor Shower

Vue d'ensemble

Pluie de meteores nocturne. Pendant 15 a 30 minutes, des EntityMeteor tombent du ciel dans une zone circulaire autour d'un point central. Chaque impact cree une petite explosion et drop du butin (ressources rares brutes, fragments d'artefact).

Ciel (Y=200) . . . . *.. . . . . .*. . . . . . . .* . . . \ \ \ \ \ \ trail de particules de feu \ \ \ * * * impact AOE 8 blocs _____________________________________ terrain Erinium Zone circulaire spawn : rayon 500 blocs autour du spawn ou point random

Deroulement

  1. Setup (onStart) : choisit un center = BlockPos aleatoire dans le monde (en evitant les claims premium et les zones safe). Charge la loot table.
  2. Phase active : toutes les spawnIntervalTicks (defaut 20 = 1 sec), spawn 1 a 5 meteors a des positions aleatoires dans le rayon de spawn. Hauteur Y=200, velocite verticale -0.8 par tick, particules FLAME + SMOKE_LARGE en trail.
  3. Impact : au contact du sol ou d'un bloc, l'entite genere une explosion (level 0=visuelle uniquement, 1=light 1.0F, 2=heavy 3.0F). Drop la loot table dans un rayon de 4 blocs au sol.
  4. Decroissance : les 2 dernieres minutes, le taux de spawn est divise par 2 puis 4 puis 0.
  5. Fin : nettoyage des entites meteor restantes, des items au sol non ramasses (apres 5 min de grace).

EntityMeteor

public class EntityMeteor extends Entity { int impactLevel; // 0=visuel, 1=light, 2=heavy ResourceLocation lootTable; UUID eventInstanceId; // Lien vers EventInstance parente @Override public void onUpdate() { motionY -= 0.08; // Trail particles client-side // Collision check if (collided) impact(); } private void impact() { // Explosion configurable if (impactLevel >= 1) world.createExplosion(null, posX, posY, posZ, impactLevel == 2 ? 3.0F : 1.0F, false); // Drop loot LootTable table = world.getLootTableManager().getLootTableFromLocation(lootTable); List<ItemStack> drops = table.generateLootForPools(...); for (ItemStack st : drops) InventoryHelper.spawnItemStack(world, posX, posY, posZ, st); setDead(); } }

Butin a recuperer vite

  • Despawn naturel : les EntityItem drop au sol respectent le despawn vanilla (5 min) — incite a ramasser vite.
  • Compteur pickups : chaque ItemStack ramasse est compte dans EventInstance.pickups.merge(uuid, 1, Integer::sum). Sert aux stats joueur.
  • PvX : rien n'empeche les factions de se battre pour les zones d'impact. C'est tout l'interet de l'event.

Conditions

  • Nuit only : requiresNight() = true. Le spawn ne commence qu'en nuit. Si la nuit se termine, l'event continue mais ne spawn plus rien.
  • Min players : 15 joueurs en ligne par defaut.
  • Pas pendant Boss Mondial : canRunConcurrently(WorldBossEvent) = false.
⚠
Performance : 100-300 entites Meteor simultanees impactent le TPS. Optimisations obligatoires : pas d'AI ticking (override onUpdate minimal), pas de tracking par tous les joueurs (custom getEntityTrackingRange = 128), batch des particules client en envoyant des packets SPacketParticles groupes. Le spawn rate doit s'auto-reduire si TPS < 18.

07 Rift Dimensionnel

Vue d'ensemble

Pendant 30 minutes, 1 a 3 portails dimensionnels apparaissent a des positions aleatoires dans le monde. Chaque portail est un bloc custom avec un TESR (particules portales). Entrer dans un portail teleporte le joueur dans une instance mini-donjon generee dans une dimension dediee. Survivre aux waves de mobs et tuer le boss du donjon donne acces a un butin rare.

Monde Erinium Dimension Rift (custom) +--------------------+ +---------------------+ | ~~ ~~ * ~~ ~~ | | Layout pre-genere | | ~ * portail | --teleport--> | (3-5 templates JSON)| | ~~~ | | Waves mobs custom | | | | Boss de fin | +--------------------+ +---------------------+ Apres 30 min : portails se ferment, joueurs encore dedans = ejectes.

Spawn des portails

  • Nombre : 1 a 3 portails par event (random configurable).
  • Position : choisie aleatoirement dans un rayon de 2000 blocs autour du spawn, surface (hauteur du terrain + 1), hors claims faction, hors safe zones, hors ocean.
  • Distance min entre portails : 500 blocs.
  • Bloc BlockRiftPortal : bloc place dans le monde, hitbox personnalisee (1x2x1), opacite 0 (lumiere passe), particules portales emises chaque tick cote client.
  • TileEntity : TileEntityRiftPortal stocke l'UUID de l'instance d'event parente et la liste des joueurs ayant deja utilise ce portail.
  • Interaction : onEntityCollidedWithBlock teleporte le joueur dans la dimension Rift. Cooldown 5 sec par joueur pour eviter le ping-pong.

Dimension Rift

Dimension custom dediee aux donjons Rift. ID configurable (defaut 50). Provider custom WorldProviderRift : ciel noir, brouillard violet, pas de meteo, no spawn naturel.

  • Instance par event : chaque event Rift cree son instance dans la meme dimension. Les instances sont separees par leurs coordonnees (x = instanceIndex * 10000, evite les collisions).
  • Generation : au onStart de l'event Rift, charge un layout JSON aleatoire parmi 3-5 templates dans config/eriniumfaction/events/rift/layouts/. Format : grille de blocs + positions de spawn de mobs + position de boss + zone de loot.
  • Layouts : ruine ancienne, temple inverse, labyrinthe cristallin, void platform, eclats Aetherite. Chaque layout est une structure de 50x30x50 blocs prepenchee.

Waves de mobs

  • 3 waves : faibles (8-15 mobs), moyennes (15-25 mobs avec elites), finale (10 mobs forts).
  • Trigger : chaque wave demarre quand la precedente est vide ou apres un timeout (3 min).
  • Mobs custom : Rift Shade (squelette violet rapide), Rift Brute (zombie tank), Rift Wisp (vex aerien), Rift Elite (boss mini avec abilites).
  • Boss de fin : spawn apres la wave 3. EntityRiftKeeper, HP 500-1500, 2 phases. Drop le butin rare.

Butin

SourceItems possibles
Mobs wavesEris (5-25), fragments d'artefact, gemmes rares (rarete cosmetics)

Fin de l'event

  • Apres 30 min : tous les portails se ferment (bloc remplace par air). Tous les joueurs encore dans la dimension Rift sont ejectes vers leur point de mort dans Erinium (ou spawn point si invalide).
  • Cleanup : les structures de donjon sont supprimees (set blocks to air dans la chunk box) puis les chunks Rift sont unloaded.
  • Players hors ligne : si un joueur etait dans le Rift et s'est deconnecte, il est teleporte a son spawn au login. Items conserves.
⚠
Anti-griefing intra-Rift : les claims faction ne sont pas actifs dans la dimension Rift. Cela permet le PvP libre, mais empeche aussi la pose de blocs (anti-rage-quit "je bloque le portail"). Le placement de blocs est interdit cote serveur dans la dimension Rift via un PlayerInteractEvent annule sur la dim.

08 Marche Noir Ambulant

Vue d'ensemble

Un PNJ marchand mysterieux spawn quelque part dans le monde et reste actif pendant 1 heure ou jusqu'a epuisement de son stock. Il vend des items rares ou interdits ailleurs, en Dollars et en Eris. Les joueurs doivent le trouver et acheter rapidement avant qu'il ne disparaisse ou que le stock soit pris par d'autres.

EntityBlackMarketMerchant

  • Base : EntityCreature custom (extends EntityVillager pour reutiliser l'IA wandering, mais override le metier et le rendu).
  • Skin : texture custom sombre (cape noire, capuche, yeux rouges). ResourceLocation custom.
  • Nom : setCustomNameTag("§c§l??? Marchand Noir"), visible toujours.
  • Invulnerable : setEntityInvulnerable(true) — impossible de le tuer.
  • Persistant : enablePersistence() — pas de despawn vanilla.
  • AI : tres limitee. EntityAILookIdle, EntityAIWatchClosest. Pas de wander.
  • Interaction : override processInteract pour ouvrir GuiBlackMarket via IGuiHandler.

Position de spawn

  • Aleatoire dans rayon : 1500 blocs autour du spawn principal.
  • Contraintes : chunk loaded ou loadable, surface (terrain + 1 a 3 blocs au-dessus du sol), hors claims faction, hors safe zones, biome navigable (pas en plein milieu d'un ocean).
  • Indices d'annonce : "Le marchand est apparu dans le secteur [N/S/E/W]" + biome dominant ("a proximite d'une foret"). Pas de coordonnees exactes.
  • Particules ambiantes : particules SMOKE_NORMAL + ENCHANTMENT_TABLE autour, visibles a 50 blocs.

Stocks et inventaire

  • 5 a 10 items distincts rotation aleatoire definie par config.
  • Stock global limite : chaque item a un nombre d'unites disponibles pour tout le serveur (ex : "Cle HDV premium x10"). Si 10 joueurs achetent 1, l'item est epuise.
  • Prix mixtes : certains items en Dollars (premium normal), d'autres en Eris (premium rare), d'autres en mix (1000$ + 50 Eris).
  • Update temps reel : chaque achat broadcast un packet de mise a jour aux clients ayant le GUI ouvert.

GUI

Achat

  • Clic sur un item : ouvre une confirmation "Acheter [item] pour [prix] ? [Oui][Non]".
  • Validation serveur : verifie solde joueur, stock restant, debit, credit item dans l'inventaire (fallback mail si plein).
  • Log : chaque transaction logguee dans logs/events/blackmarket.log (qui, quoi, prix, timestamp).
  • Pas de refund : achat ferme. Le marchand n'achete rien aux joueurs.

Disparition

  • Timer 1h : au endTick, le marchand fait un effet de teleportation (particules PORTAL intenses, son ENTITY_ENDERMEN_TELEPORT), puis disparait.
  • Stock epuise : si tous les items sont a 0, le marchand part au prochain tick (annonce broadcast : "Le marchand noir vient de disparaitre, son stock est epuise.").
  • Cleanup : entite retiree, EventInstance passe a COMPLETED.
ⓘ
Items exclusifs : certains items vendus au Marche Noir ne sont AVAILABLE NULLE PART AILLEURS (pas au HDV, pas via /shop, pas en drop). C'est ce qui motive les joueurs a se precipiter. Ex : skin cosmetique "Marchand Noir", bandeau "VIP de la nuit", parchemin de sort rare.

09 Boss Mondial

Vue d'ensemble

Le boss ultime du systeme d'evenements. Un monstre geant spawn au centre de la map ou a un point fixe configure. Toutes les factions du serveur peuvent l'attaquer ensemble. Les recompenses sont distribuees en fonction des degats infliges par chaque joueur. Cooldown 24-48h.

EntityWorldBoss

  • Base : EntityMob custom, scale 3x-4x, HP 1,000,000 a 10,000,000 (configurable).
  • Modele : modele 3D Blockbench custom dans assets/eriniumfaction/models/entity/world_boss.json. Texture custom. TESR dedie pour rendu et animations.
  • Hitbox : 6x8x6 environ. getRenderBoundingBox() override (10x12x10) pour eviter frustum culling.
  • Knockback resistance : 1.0 (immune au knockback).
  • Pas de despawn naturel.
  • Damage cap : aucun degat unique > 5% de l'HP max (anti-onesho via items glitch).

Phases

PhaseDeclenchementPatterns
1 (Eveil)HP > 66%Attaques au sol (sweep AOE), invocation de petits mobs (Rift Shades x6 toutes les 30 sec)
2 (Furie)HP 66% - 33%Projectiles a tete chercheuse (3 par seconde), zones empoisonnees au sol (rayon 4), regen lent (1k HP/sec)
3 (Desespoir)HP < 33%Charge frontale (knockback massif), explosion AOE periodique (rayon 12, 20 sec cooldown), invocation d'elites

WorldBossAI

  • Ciblage : selectionne le joueur le plus proche dans un rayon de 32 blocs comme cible principale, change toutes les 10 sec.
  • Patterns : chaque pattern est une BossAttackPattern avec cooldown, cast time, execute(). Pool different par phase.
  • Selection pattern : chaque cooldown, choisit aleatoirement un pattern dispo dans la phase courante.

Tracking des degats

Hook sur LivingHurtEvent filtre sur l'entite boss. Chaque hit incremente EventInstance.damageDealt.merge(uuid, damage, Long::sum). La BossBar du boss est visible par tous les joueurs en ligne (pas seulement proches), HP affichee globalement.

Distribution du butin

Au onEnd (kill du boss) :

  1. Trier damageDealt par valeur decroissante.
  2. Killer (Top 1) : 25% du loot pool + bonus "Premier Sang" : 1 artefact legendaire garanti.
  3. Top 2 a 10 : repartition ponderee selon le % de degats de chaque joueur dans le total. Items : artefacts rares/epiques, lootbox tier 3, Eris (1000-5000 par joueur).
  4. Damagers > 1% du total : butin de consolation. 1 lootbox tier 1 + 100 Eris.
  5. Damage < 1% : 50 Eris (anti-leech : participation symbolique).

Livraison : tous les joueurs (en ligne ou non) recoivent le butin via le systeme Mail (MailSenderType.EVENT_REWARD) avec un message detaillant les degats infliges et leur rang.

Spawn

  • Position : centre de la map (par defaut (0, surface, 0)) ou worldBoss.spawnPoint configurable.
  • Annonce : les annonces T-10/T-1/T-0 incluent une mention "Le boss mondial s'eveille au coeur du monde !" + coordonnees exactes (pas de mystere ici, l'event est public).
  • Effet visuel : au spawn, vortex de nuages sombres visible a 500 blocs, eclairs EntityLightningBolt repetes pendant 10 secondes.

Mort / Fin

  • Kill : distribution butin, message "Le boss mondial a ete vaincu par [killer] avec l'aide de [N] joueurs !".
  • Timeout : si le boss n'est pas tue dans la duree maximale (defaut 90 min), il "fuit". Distribution partielle du butin (50% des recompenses Top 10, rien pour les autres). Message "Le boss s'echappe..."
  • Despawn : entite retiree, EventInstance COMPLETED. Cooldown 24-48h avant le prochain.
⚠
Anti-exploit : les degats venant de creatures controlees par d'autres mods (pets, mobs), d'effets sources (fall damage, dot non sourcees), ou de joueurs en mode Spectateur sont ignores dans damageDealt. Seuls les degats source direct par EntityPlayerMP en mode Survival/Adventure sont comptes. Anti-AFK : si un joueur tape 1 fois puis reste AFK 10 min, ses degats sont retenus mais il ne peut pas faire partie du Top 10 (flag activelyEngaging).

12 Cas Limites & Performance

Crash serveur pendant un event

  • WorldSavedData : EventSavedData.markDirty() appele toutes les minutes pendant un event actif. Au crash, on perd au pire 60 secondes d'etat.
  • Reprise au boot : EventManager.init() lit les events ACTIVE depuis la WSD et les reinstancie. Le endTick est recalcule : endTick = currentTick + (originalEndTick - savedTick).
  • Entites disparues : si une entite critique (boss, marchand) a disparu au reboot, l'event est annule avec compensation (Eris) aux joueurs ayant deja contribue.

Serveur vide ou en sous-effectif

  • Min players : si < events.minPlayersOnline en ligne, aucun nouvel event ne se declenche. Les events deja actifs continuent.
  • Reprise au retour des joueurs : le scheduler reprend des que la condition est remplie.

Events simultanes

  • Max 2 par defaut : events.maxConcurrent. Si 2 events tournent, aucun autre ne peut commencer.
  • Boss exclusif : WorldBossEvent.canRunConcurrently() retourne false pour tout. Si un Boss est actif, aucun autre event ne peut tourner. Si un autre event est actif, le Boss attend qu'il se termine.
  • Compatibilite : Meteor + Rift OK, Marche + Rift OK, Marche + Meteor OK, Boss + rien (sauf Marche Noir qui est passif et peut coexister).

Performance et TPS

  • Entites custom cap : chaque event a une limite stricte d'entites (Meteor: 50 simultanees max, Rift: 30 mobs par instance, Boss: 1 + 10 minions).
  • AI ticking optimise : les EntityMeteor n'ont aucune AI. Le boss a une AI custom executee tous les 5 ticks (pas chaque tick).
  • Chunk loading : les chunks d'event sont force-loaded uniquement pendant l'event actif et sont unloaded au onEnd. Utilisation de ForgeChunkManager.Ticket via ticket persistant.
  • Auto-degradation TPS : si TPS < 18 pendant > 30 sec pendant un event Meteor : taux de spawn divise par 2. Si < 16 : divise par 4. Si < 14 : spawn arrete completement.
  • Batch packets : les annonces, bossbar updates, et particules sont batchees a 4 Hz max (5 ticks d'intervalle).
  • Cout cible : tout event ne doit jamais depasser 2 ms/tick mesure sur Spark/Timings (hors pic ponctuels d'explosion).

Conflits avec claims faction

  • Spawn : les events Meteor, Rift, Marche Noir refusent de spawn dans un claim faction. Recherche d'un nouveau point jusqu'a 10 tentatives, sinon abort de l'event.
  • Boss Mondial : exception. Spawn force au point configure (centre), meme si claim. Le proprietaire du claim ne peut pas empecher le boss de spawn. Le PvP/dmg dans le claim pendant le boss n'est pas active (claims restent actifs sauf pour le boss lui-meme).
  • Loot drop : les items drops par les events ne respectent pas les claims (anyone can pick up).

Joueurs hors ligne

  • Joueur deconnecte pendant un event : ses contributions restent comptees. Au end, son butin est envoye par mail.
  • Player dans Rift au logout : au login, le joueur est teleporte a son point de spawn dans Erinium.

Trade / interactions pendant event

  • Pas de restriction speciale. Les joueurs peuvent commercer, ouvrir le HDV, etc. pendant un event.
⚠
Risque PvP-fest : les zones d'event sont des hot-spots de PvP. Anti-camping requis : si une faction "claim" le centre d'un event (ex : barricades autour d'un portail Rift), le serveur n'empeche pas le PvP — c'est l'esprit du systeme. Mais le placement de blocs autour des spawns Rift est detecte et nettoye apres la fin de l'event.

13 Integration Autres Systemes

Mail (livraison butin hors ligne)

  • API : MailManager.getInstance().sendMail(UUID, ...) avec MailSenderType.EVENT_REWARD.
  • Butin Boss : tous les contributeurs recoivent un mail, en ligne ou non.
  • Inventaire plein : achat Marche Noir avec inventaire plein -> item livre par mail.
  • Compensation event annule : Eris envoyes par mail aux contributeurs.

Faction (visibilite GUI faction)

  • Onglet "Evenements" : dans la GUI faction, ajout d'un onglet listant les events actifs et l'historique des participations de la faction.
  • Stats faction : nombre de boss tues par la faction (somme des contributions de ses membres > 5%).

Profil / Stats joueur

  • Ajouter dans PlayerProfileData les compteurs :
  • eventsParticipated : total events ou le joueur a contribue.
  • worldBossKills : nombre de fois ou il faisait partie du Top 10 d'un kill boss.
  • meteorsCollected : total drops Meteor ramasses.
  • riftCompleted : nombre de Rift termines (boss Rift Keeper tue).
  • blackMarketBought : nombre d'items achetes au Marche Noir.
  • Affichage : page Stats du profil sur le site web + commande /profile stats.

Discord (webhook)

  • events.discordWebhookUrl : si configure, l'EventAnnouncer envoie un POST JSON au webhook lors des annonces T-10 et T-0.
  • Format embed : titre = nom event, couleur = couleur event, description = "Demarre dans 10 min !", thumbnail = icone event.
  • Async : appels HTTP via un thread pool dedie pour ne pas bloquer le tick serveur. Echec silencieux logge.

HDV (revente du butin)

  • Les items legendaires/artefacts dropes par les events peuvent etre revendus au HDV (pas blacklisted).
  • Exception : les items "Marche Noir exclusifs" (skins, capes) sont liés au joueur (NBT SoulBound) et non revendables au HDV.

EriAPI (modules utilises)

  • EriScheduler : ticks recurrents du EventManager, delays pour annonces.
  • EriEvents : hook ServerTickEvent, LivingHurtEvent (boss dmg tracking), EntityJoinWorldEvent (cleanup), PlayerEvent.PlayerLoggedInEvent (reprise Rift).
  • EriChat : messages d'annonce formates avec gradients, hovers, clicks.
  • OverlayMod : toast d'annonce client-side (S5).
  • GuiNetworkHandler : ouverture du GUI Marche Noir, packets de stock.
