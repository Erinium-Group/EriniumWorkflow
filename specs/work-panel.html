01 Contexte & Objectifs

Vision du systeme

Le Work Panel est l'espace de travail prive du staff EriniumFaction. Il remplace toute coordination eparpillee (Discord, Trello, Google Sheets) par un panel integre au site web admin, avec des permissions fines, une boucle de feedback rapide entre le site et le serveur Minecraft live, et un design coherent avec le reste du site (Liquid Glass iOS 26).

Le panel est concu pour une equipe de 5 a 25 staff avec une rotation reguliere (admins permanents, modos saisonniers, builders ponctuels). Chaque membre voit uniquement ce que son ou ses roles l'autorisent a voir. Aucune action staff ne devrait se faire ailleurs que dans ce panel — c'est la source unique de verite operationnelle.

Objectifs de design

  • Source unique : annonces, tickets, taches, documentation, calendrier — tout est au meme endroit. Plus de "ou est passe le ticket de X ?" sur Discord.
  • Granularite RBAC : chaque feature (workspaces, boards, cartes, events, tickets, annonces, articles, roles, webhooks, audit) a 4 actions CRUD distinctes. Un role = 48 toggles maximum.
  • Multi-roles cumulables : un staff peut etre moderator + builder + event_team. Les permissions s'additionnent (union ensembliste).
  • Sync Google Calendar par staff : chaque membre lie son propre compte Google, choisit quels calendriers exposer, et beneficie d'une sync bidirectionnelle (events du panel pousses dans Google, events Google importes en lecture).
  • Workspaces a la demande : n'importe quel staff avec la permission workspaces.create peut creer un workspace. Pas de provisioning admin requis.
  • Lien direct serveur MC : chaque carte/ticket peut referencer un joueur in-game (UUID + nom MC), avec un bouton "Voir le joueur" qui appelle l'API MC port 8081 et un bouton "Executer commande" pour les permissions adequates.
  • Performance : le panel charge en moins de 1.5s sur une connexion 4G. Le Kanban supporte 500+ cartes par board sans lag (virtualisation), les calendriers gerent 1000+ events/mois avec rendering progressif.
  • Auditabilite : 100% des actions sensibles (changement de role, suppression de carte, exec commande MC, suppression d'evenement) sont loggees avec acteur + cible + diff + timestamp + IP.

Ce que le systeme ne fait pas

  • Pas un Discord-bis : pas de salons texte temps reel, pas de DM. Le chat staff reste sur Discord. Le panel se limite aux commentaires sur cartes/tickets et aux mentions @user.
  • Pas un IDE : pas de gestion de code, pas de pull requests, pas de CI/CD. C'est strictement un panel operationnel.
  • Pas de gestion de paie : aucune donnee financiere ou contractuelle. Reste sur des outils RH externes.
  • Pas d'acces public : tout le panel est derriere une auth Discord OAuth + verification du flag staffRole != null. Aucune route publique.
ⓘ
Public cible : 5 a 25 membres staff actifs. L'interface est optimisee pour ce volume — pas d'overengineering pour 1000 utilisateurs simultanes. Les requetes Neon Postgres restent simples (pas de sharding), le cache permissions est trivial (en memoire serverless + invalidation par perms_version).

Decisions architecturales

  • Server Components par defaut : chaque page server-fetch ses donnees (workspaces, boards, calendar events) avec auth+permissions check. Les composants client se limitent au Kanban, calendar, modaux et inputs interactifs.
  • API routes versionnees : toutes les routes Work Panel sous /api/work/v1/... pour permettre une migration future sans casser le launcher ou les integrations externes.
  • Cache permissions in-memory + version : chaque Serverless Function maintient une Map<userId, { version, perms }> en module-level (chaud entre invocations sur meme instance). Lookup : on lit users.perms_version (requete unique indexee), si match on retourne le cache, sinon on re-fetch et on met a jour. Bump = UPDATE users SET perms_version = perms_version + 1. Cold start = miss = recalcul (acceptable, < 50ms).
  • WebSockets non requis V1 : notifications + Kanban refresh via polling intelligent (react-query refetchOnWindowFocus + intervals adaptatifs 30s/60s/300s selon onglet visible). Si besoin temps reel V2 : Pusher Channels ou Ably (SaaS WebSocket compatible Vercel) — pas de Durable Objects (incompatible Vercel).
  • Realtime degrade : les changements faits par un staff apparaissent chez les autres avec un delai de 30 a 60 secondes. Acceptable pour 5-25 utilisateurs sur des operations non concurrentielles.
⚠
Auth obligatoire sur 100% des routes : chaque /api/work/v1/* commence par await requireStaff(request) qui (a) verifie la session JWT (cookie httpOnly via jose), (b) charge le user depuis Neon, (c) verifie qu'il a au moins un role staff via staff_user_roles, (d) charge les permissions resolved (cache LRU + perms_version), (e) verifie la permission demandee. Toute route qui oublie cette etape est un bug critique.

04 Roles, Badges & Permissions

Principes

  • Multi-roles cumulables : un user peut avoir 0, 1, ou N roles via staff_user_roles. Aucun role n'est exclusif.
  • Union ensembliste : les permissions effectives = UNION des permissions de tous les roles. Pas de soustraction, pas de hierarchie.
  • Granularite CRUD : chaque feature a 4 actions : create, read, update, delete. 12 features × 4 = 48 permissions max par role.
  • Wildcard : la permission * dans staff_role_permissions donne tous les droits (role owner uniquement).
  • Affichage badges : tous les roles du user sont affiches comme petits chips colores (couleur + icone + nom). Triables par priority.

// src/lib/work/permissions.ts import { query } from "@/lib/db"; // Cache LRU process-level — chaud entre invocations sur la meme instance serverless. // Reinitialise au cold start (acceptable : recalcul < 50ms). const CACHE = new Map<number, { version: number; perms: Set<string> }>(); const MAX_ENTRIES = 200; export async function resolvePermissions(userId: number): Promise<Set<string>> { // 1. Lookup version (1 query indexee, < 5ms sur Neon) const vRows = await query("SELECT perms_version FROM users WHERE id = $1", [userId]); const version = Number(vRows[0]?.perms_version ?? 0); // 2. 10 Sync Google Calendar (OAuth per-user)

Principe

Chaque staff lie SON propre compte Google. Pas de compte central. Pas de Service Account. Ainsi : (a) chaque staff garde controle sur ses donnees, (b) on respecte le RGPD, (c) on peut afficher les vrais events du staff (familiaux, perso) en lecture seule sur sa vue calendrier (avec opt-in).

Flow OAuth

/admin/work/settings/google | click "Lier mon Google Calendar" v GET /api/work/v1/google/oauth/start | redirige vers accounts.google.com v User accepte scope calendar.events + calendar.readonly | google redirige vers v GET /api/work/v1/google/oauth/callback?code=... | echange code -> access_token + refresh_token | chiffre AES-GCM | stocke dans users.google_calendar_tokens v Redirige vers /admin/work/settings/google?linked=1

Stockage tokens (chiffrement)

  • Cle de chiffrement : process.env.GOOGLE_ENC_KEY (32 bytes hex, variable d'env Vercel — provisionnee via Vercel Dashboard ou vercel env add).
  • Algorithme : AES-256-GCM. Stocke en base64 dans users.google_calendar_tokens sous forme : {access:..., refresh:..., expires_at:..., scope:..., iv:...}.
  • Refresh automatique 5 min avant expires_at, transparent pour le user.
  • Bouton "Delier" => revoke token Google + clear field.

Direction de sync

SensComportement

Frequence de sync

  • Push panel => Google : immediate (au moment de la creation/update).
  • Pull Google => panel : Vercel Cron Job (vercel.json > crons) declenchant /api/work/v1/google/sync-pull toutes les 15 minutes. La route itere tous les users lies en mode batch (max 30s execution serverless). Incremental sync via nextSyncToken Google stocke par user.
  • Manuel : bouton "Re-synchroniser maintenant" dans settings.

UI Settings

  • Page /admin/work/settings/google : statut (lie / non lie), liste des calendriers Google avec toggle "Importer celui-ci", bouton "Delier".
  • Selecteur "Pousser mes events du panel dans :" (calendrier Google par defaut, ou je choisis lequel).
  • Toggle "Inclure les events kind=absence" (pour eviter de pousser ses conges sur Google si pas voulu).

Vision

Permettre de poster automatiquement dans un canal Discord quand certains evenements se produisent dans le Work Panel. Configurable par admin.

Modele

  • Un webhook = un nom + une URL Discord (chiffree AES-GCM) + liste d'events watched + filtre workspace optionnel + enabled.

  • Edit URL : confirmation obligatoire.

  • card.create, card.complete, card.high_priority_created

// src/app/api/work/v1/cards/route.ts import { NextRequest, NextResponse } from "next/server"; import { requireStaff } from "@/lib/work/permissions"; import { query } from "@/lib/db"; import { logAudit } from "@/lib/work/audit"; import { dispatchEvent } from "@/lib/work/webhooks"; import { z } from "zod"; const CreateSchema = z.object({ column_id: z.number().int(), title: z.string().min(1).max(200), description: z.string().optional(), sort_order: z.number().int(), priority: z.enum(["low", "medium", "high", "critical"]).nullable(), due_at: z.string().datetime().nullable(), }); export async function POST(req: NextRequest) { const { user } = await requireStaff(req, "cards.create"); const body = CreateSchema.parse(await req.json()); const rows = await query(` INSERT INTO cards (column_id, title, description, sort_order, priority, due_at, created_by) VALUES ($1, $2, $3, $4, $5, $6, $7) RETURNING * `, [body.column_id, body.title, body.description, body.sort_order, body.priority, body.due_at, user.id]); const card = rows[0]; await logAudit({ actor: user.id, action: "card.create", target_type: "card", target_id: card.id, diff: { after: card } }); await dispatchEvent("card.create", { card, by: user }); return NextResponse.json(card); }

API REST — conventions

  • JSON partout. Content-Type: application/json. Runtime nodejs (pas edge car Neon driver + jose + googleapis necessitent Node).
  • Erreurs : { error: "CODE", message: "Description humaine", details?: {...} } + status HTTP approprie (400/401/403/404/409/429/500).
  • Pagination : ?cursor=&limit=. Reponse { items: [], nextCursor: "..." }.
  • Filtres : query params ?status=open&assigned_to=42.
  • ETag/If-Match pour les updates concurrentes sur cartes.
  • Validation des bodies par zod systematique (existant deja dans le projet via TipTap usage).

Cron jobs Vercel

Definis dans vercel.json > crons. Plan Vercel Pro requis pour intervalles < 1h (sinon 1 cron / 24h max sur Hobby).

// vercel.json (extrait) { "crons": [ { "path": "/api/work/v1/cron/notifications-tick", "schedule": "*/5 * * * *" }, { "path": "/api/work/v1/cron/google-sync-pull", "schedule": "*/15 * * * *" }, { "path": "/api/work/v1/cron/daily-compaction", "schedule": "0 3 * * *" }, { "path": "/api/work/v1/cron/monthly-purge", "schedule": "0 4 1 * *" } ] }
  • Toutes les 5 min (notifications-tick) : rappels due_soon sur cartes, event_reminder 15min avant evenement.
  • Toutes les 15 min (google-sync-pull) : pull Google Calendar pour chaque user lie (batch, max 30s execution serverless).
  • Quotidien 3h UTC (daily-compaction) : compactage sort_order des colonnes / cartes, purge soft des cartes archivees > 90 jours.
  • Mensuel 1er a 4h (monthly-purge) : purge audit_log > 1 an, expiration annonces.
  • Securite cron : Vercel envoie un header Authorization: Bearer ${'$'}{CRON_SECRET} — chaque route cron verifie ce header et retourne 401 sinon.
